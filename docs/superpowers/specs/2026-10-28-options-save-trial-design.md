# 設定画面の保存分離と初回お試し 設計書

PBI-161（保存分離）と PBI-162（初回ダミー）の設計を定める。基本設計は `2026-10-03-jushoai-design.md`、複数プロファイルは `2026-10-05-profiles-design.md` に従い、この文書は変更点だけを定める。

## 目的とスコープ

- プロファイルだけ入力して保存できるようにし、不可視の住所エラーで迷わせない
- 初回（有効プロファイルなし）の利用者が、架空データで操作と自動入力を試せるようにする

### 含める

- オプション画面の保存分離：プロファイル画面はプロファイルだけ、住所画面は住所だけを検証・保存。各画面に保存ボタン
- 保存成功時の反対側への誘導（タブ移動手段付きメッセージ）
- 初回判定（有効プロファイルなし）と両画面先頭の案内バナー＋お試し入力ボタン
- 新規 `src/core/sample-data.ts` の純粋関数 `makeSampleProfile`／`makeSampleAddress`（依存ゼロ、毎回別人物、検証通過保証）
- お試し入力は空欄だけ埋める・入力済み不変・自動保存なし

### 含めない

- `isReady`・注入・分類ロジックの変更
- Faker.js（`@faker-js/faker`）の導入
- 海外住所ダミー、自動保存、下書き保存（検証緩和）
- プロファイル・住所の並べ替え、件数上限の変更

## 現状と原因

- `src/entrypoints/options/main.ts` の `onSave` は `validateProfile` と `validateAddress` を一括で検証する単一保存ボタン
- ナビ（`nav.ts` の `applyActivePage`）ではプロファイルと住所は別ページ表示だが、フッターは共有のため、プロファイル編集中に不可視の住所エラー（自宅：郵便番号・都道府県・市区町村・番地）が出る
- 初回は空のプロファイルカード＋空の住所カード（ラベル「自宅」）から始まるため、何を入れれば保存できるかが分かりにくい。本物データの入力に抵抗がある利用者は試用で離脱する
- ダミー生成・お試しUIは未実装（2026-10-28 確認）。`package.json` の `dependencies` は空

## アーキテクチャ

```
プロファイル画面 ── onSaveProfiles ── normalizeProfile → validateProfileのみ ── saveData（ID単位マージ）
住所画面       ── onSaveAddresses ── normalizeAddress → validateAddressのみ ── saveData（ID単位マージ）
成功時 ── 反対側が未完成なら誘導メッセージ＋タブ移動ボタン（setActivePage）
初回（有効プロファイル0件）のみ ── 両画面先頭に案内バナー ──［お試し入力］── sample-data → 空欄だけ埋めて再描画（保存は各画面の保存に委ねる）
```

- 分類・注入・承認フローは無改変。`core/` は DOM・LLM 非依存の方針を維持し、`sample-data.ts` も純粋関数とする
- `saveData` の ID 単位マージ（incoming wins、空配列では反対側が残る）を利用し、片側保存で反対側を消さない

## データモデル・保存

- `Profile`／`Address`／`StoredData` の型変更なし
- プロファイル保存：`state.profiles.map(normalizeProfile)` を検証し、不備がなければ `saveData` へ。住所の状態は見ない。0件チェックはプロファイル側のみ
- 住所保存：`state.addresses.map(normalizeAddress)` を検証し、不備がなければ `saveData` へ。プロファイルの状態は見ない。0件チェックは住所側のみ
- エラー表示は今見ている画面の項目のみ。不可視の反対側エラーは出さない。反対側未完成は成功メッセージ内の誘導で扱う
- 取り込みボタン「フォームから取り込む」は両画面に残す。draft は両方を埋めるが、保存は各画面で確定する

## UI

### 保存ボタン

- 共有フッターを廃止し、プロファイルページと住所ページにそれぞれ保存ボタンを置く
- プロファイル保存成功＋有効住所なし（`validateAddress` 通過が0件）→ 「保存しました。次は住所を入力してください」＋住所タブへ移動ボタン
- 住所保存成功＋有効プロファイルなし（`validateProfile` 通過が0件）→ 逆方向の同型誘導（通常は起きないが対称に用意）
- 両方完成時 → 「保存しました」のみ
- 転記セクション（JSON エクスポート／インポート）は従来通り共通下部に残し、保存ボタン分離の影響を受けない

### 初回案内バナー

- 表示条件：`state.profiles` に `validateProfile` 通過が0件のときのみ。プロファイル画面と住所画面の両方の先頭に出す
- 文言例：「初めてですか？架空の名前と住所で試せます［お試し入力］」
- 有効プロファイルが1件でもできたら非表示
- ボタン押下：空欄だけを架空値で埋め、入力済みは消さない。カードが0件の側は先に1件作ってから埋める（成功表示に見合う実体を残す）。自動保存はしない（保存ボタンを押す体験につなげる）

## ダミー生成（`core/sample-data.ts`）

Fakerは不採用。理由は2点。第一にバンドルが約1MB級で増え MV3 拡張には重い。第二に ja ロケールの住所が `validateAddress` の正式名称制約とずれるため結局マッピング層が要り、自前と同量の整形コードになる。

自前生成の仕様：

- `makeSampleProfile(random)`：名字・名前＋セイ・メイ対照表（20件前後）から選択、ローマ字対照、メール派生、電話は 090/080＋8桁数字、誕生日は実在日ランダム（ISO YYYY-MM-DD）
- `makeSampleAddress(random)`：都道府県は既存 `PREFECTURES` から選択、市区・番地テンプレート、郵便番号7桁数字、建物名は任意で付与
- 乱数は `crypto.getRandomValues` を使用。名字とカナ・ローマ字の対応は崩さない（別々に乱数引きしない）
- 電話・郵便番号は数字整形済みで返す（`normalize` 任せにしない）
- 生成値は必ず `validateProfile`／`validateAddress` を通過する。単体テストで反復検証する
- 外部送信なし・永続化なし（入力欄に流すだけ）

## テスト

- **単体**（`tests/core/sample-data.test.ts`）：検証通過（反復試行）、連続生成の多様性、セイ・メイ全角カナ、郵便番号7桁、都道府県が正式名称、電話10〜11桁、誕生日実在日。保存分離の検証スコープ（各側のみ見ること）
- **統合**：初回判定で両画面にバナーが出ること、有効化後に消えること、入力済み保持と未保存の確認、誘導ボタンのタブ遷移
- **E2E／手動**：初回→お試し→プロファイル保存→誘導→住所保存の通し確認。エントリポイントの単体テストは作らない既存方針に従い、画面振る舞いは typecheck＋手動で担保
- `make check` が緑であること

## 完了判定

1. `make check`（typecheck＋test＋build）が緑
2. 目視確認：プロファイルのみ保存成功し住所エラーが出ないこと、成功表示の誘導から住所画面へ移動できること、初回バナー→お試し→各保存の流れが通ること、お試しで入力済みが消えず自動保存されないこと

## 要検討（スコープ外として記録）

- 海外住所ダミーの生成
- お試しデータのバリエーション拡充（職業・会社名など）
- 下書き保存や検証緩和の導入
