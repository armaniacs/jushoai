# なぜなぜ分析 30 回 — 実装をどこまで自律的に進められるか（2026-10-11）

## 対象と問い

- 対象: egress ゲートのラウンド（PBI 04・05）の実装、および決定済み実施順（04 → 05 → 07…）に従う後続の実装。
- 問い: 「この後の実装を、どこまで自律的に進められるか。滞る点・利用者の判断が要る点はどこか」
- 方法: なぜなぜ分析を 30 回繰り返し、滞り得る要素を「判断 / 検証 / 記録」の 3 系統に分解して根本原因まで掘る。ゴール（goal-61072a1c）の継続ランから参照する。

## 30 のなぜなぜ

### A. 判断は滞らないか（1〜12）

1. **なぜ 04 の実装が滞る可能性があるのか** → 未実装は「リゾルバ origin の要求」と「fail-closed」の 2 点だが、実装手順 9 段と落とし穴が PBI 本文に確定しているか、着手時点では未確認だから。
   → PBI を全文読み、手順と落とし穴を確定した。滞り得る要素は「判断」「検証」「記録」の 3 系統に集約される。
2. **なぜ「判断」が滞り得る要素なのか** → 実装中に 2 つの設計判断（verified フラグ、可用性の返し方）に突き当たるから。
3. **なぜ verified フラグの判断で滞らないのか** → PBI の未決節が「落とす」を推奨し、代替（残して常に true をテストで固定）も条件付きで許している。推奨に従えば判断済み。→ 自律的に決定: **落とす**。
4. **なぜ可用性の返し方で滞らないのか** → PBI が「本 PBI では実装せず、必要なら別 PBI」を推奨し、`WHY-30-EGRESS-FAIL-CLOSED.md` の行動順も fail-closed 先行を導いている。→ 自律的に決定: **実装しない。台帳に記録のみ**。
5. **なぜ fail-closed の採否自体で滞らないのか** → 30 のなぜなぜが fail-closed を導き、ラウンド 03 台帳に記録済み。アーカイブ済み PBI `2026-10-10-04` が fail-closed を要求して `[x]` のまま。→ 要件記録と整合する解が既にある。
6. **なぜコード編集は滞らないのか** → 対象ファイル（`src/ai/`、`src/llm/`、`src/entrypoints/`、`tests/`、`site/content/`、`CHANGELOG.md`）はすべて workspace 内で、workspace-write ポリシーで編集可能だから。→ 滞らない。
7. **なぜテストの期待値を書けるのか** → 反転対象（:145・:156・:309・:391）と不変（:96・:404）を実ファイルで抽査済み。→ 着手時に検証済み。
8. **なぜ既存テストの流儀で迷わないのか** → vitest の describe/it と fake の `ResolveDeps` seam が既存で、CLAUDE.md の fixture 先行方針がある。→ 従う。
9. **なぜ docs の日英一致で滞らないのか** → `site/check.ts` が日英のキーと H2 数を検査し、片言語だと落ちる。→ 両言語同時に直す（手順 8）。
10. **なぜ CHANGELOG は滞らないのか** → Unreleased 節への追記が習慣。→ 追記する。
11. **なぜコメントの書き換えで滞らないのか** → 対象行（`settings.ts` :141-142・:167-168・:181-182・:251-252・:265-269）が列挙され、「Fail-closed の語が 2 つの意味で混ざらないように」という注意もある。→ 従う。
12. **なぜ verified を落とした場合の参照除去で滞らないのか** → `ai-section.ts` の参照は保存時ゲートの hard error 化と同時に消え、`make typecheck` が参照漏れを機械的に検出する。→ 滞らない。

### B. 検証は滞らないか（13〜20）

13. **なぜ「検証」が滞り得る要素なのか** → 自動化できる検証とできない検証があるから。
14. **なぜ make check は滞らないのか** → 依存済み・make available で全段（typecheck → test → build → test-build → lint-firefox）が自動。→ 実行して緑にする。
15. **なぜ lint-firefox が環境で失敗する可能性があるのか** → web-ext が初回ダウンロードを要する可能性。→ 失敗したら失敗内容を記録し、typecheck+test+build で前進してから対処。→ 滞っても回避手順はある。
16. **なぜ実機確認（permission prompt の実挙動・企業プロキシでの fail-closed 挙動）が自動化できないのか** → `chrome.permissions.request` の user gesture と実ネットワークは jsdom で再現不可。CLAUDE.md テスト方針が「実精度とページ上の挙動は samples/ で手動確認」と明言。→ **ユーザー作業として台帳に記録**。
17. **なぜ make e2e-firefox は試せるが保証できないのか** → `FIREFOX_BIN`・フルディスクアクセスが要り、make check に含まれない。→ 試し、失敗したらユーザー作業として記録（滞留しない）。
18. **なぜ DoH の実到達性が検証できないのか** → ネットワーク依存。テストは fake で固定するのが PBI のテスト戦略。→ 実検証はユーザー作業。
19. **なぜ監査の再確認は滞らないのか** → 再監査は別ラン。実装完了で受入基準の大半（escape hatch の記述消去、fetch しない固定、hard error 化）は満たせる。残り（再監査で確認）を台帳に記録。→ 滞らない。
20. **なぜ graphify の更新が要るのか** → CLAUDE.md の規則（コード変更後 `graphify update .`）。→ コミット時に hook が自動で走る（確認済み）。

### C. 記録は滞らないか（21〜30）

21. **なぜ「記録」が滞り得る要素なのか** → コミット・push・台帳更新の扱いが境界だから。
22. **なぜコミットは滞らないのか** → 承認ポリシーが ask で承認者が居る。プロンプトが出るが承認されれば進む。→ 滞留しない（承認待ちの間は次の手順へ）。
23. **なぜ push はしないのか** → commit スキルが「push は明示的に指示された場合のみ」と禁じている。→ **自律境界: push しない**。
24. **なぜブランチで迷わないのか** → 現在 1009a で PBI 起票コミット済み。同一ブランチ継続が既定。→ 迷わない。
25. **なぜバージョン番号の同期は不要なのか** → 本変更はコード・docs のみでバージョン番号を含まない。→ スキップ。
26. **なぜ PBI の checkbox 更新で滞らないのか** → 受け入れ基準 10 項目と DoD 6 項目が機械的に数えられ、実装コミット + make check 緑 + grep（escape hatch 消去）で `[x]` にできる基準が明確。→ 滞らない。
27. **なぜ「コードレビュー完了」が滞る可能性があるのか** → DoD に含まれるがレビューの実施者が未定義。→ 自分でレビュー（adversarial-code-review スキル）を実施して記録し、最終承認をユーザーに残す。→ 滞らない。
28. **なぜ 05 は 04 の後なのか** → 決定済み（04 → 05）。05 の Red-first テストは 04 の fail-closed が前提。→ 滞らない。
29. **なぜ 07 の設計判断を並行で確定しないのか** → 台帳 06 に「04 の実装と並行に先に確定してよい」と記録済みだが、本ゴールの範囲は 04・05。07 は次のゴール。→ 範囲外として記録（滞らない）。
30. **なぜこの分析をファイルに残すのか** → ゴールが最大 10 ラウンド自動継続するため、継続ランで再利用する。`WHY-30-EGRESS-FAIL-CLOSED.md` の前例（30 のなぜなぜをファイルに残して行動順を導いた）に倣う。→ 本ファイルとして保存し、PBI 04 から参照する。

## 解 — 自律境界の地図

### 自律でできる範囲（ユーザーの承認なしに進める）

- PBI 04 の実装手順 1〜9 の全部（テスト反転 → `requiredHostOrigins` → 差し替え 2 か所 → `verdictOf` の fail-closed 化 → 保存時ゲートの hard error 化 → コメント → docs/CHANGELOG → make check）
- 設計判断: verified フラグは**落とす**（PBI の推奨に従う）。可用性の返し方は**実装しない**（PBI の推奨に従い、台帳に記録）
- PBI 04 の受入基準・DoD のうち機械的に検証できる項目の `[x]` 化、アーカイブ、INDEX 更新
- コードレビュー（自分で adversarial に実施し、指摘を解消して記録）
- PBI 05 の実装（04 の後。ラウンド 03 台帳の条件のとおり同一コミットでも可）
- コミット（ask 承認プロンプト経由）

### 利用者の作業（滞留させないため台帳に記録する）

1. **実機確認**: permission prompt の実挙動（保存ボタンからの user gesture）、企業プロキシ等で `dns.google` が塞がれた環境での fail-closed 挙動、`http://127.0.0.1` の設計どおりのパス
2. **再監査での確認**（監査記録の blocker 解消の検証）
3. **push**（明示的に指示された場合のみ）
4. **レビューの最終承認**（自分で実施したレビューの結果を確認して受け入れる）

### 滞留時の対処

- ask 承認待ち → 待ち時間に次の手順（コミットは最後にまとめる）
- lint-firefox / e2e-firefox の環境失敗 → 失敗内容を台帳に記録し、typecheck+test+build で前進
- 未決に突き当たったら → PBI の推奨に従う。推奨がない場合は台帳に「未決」として記録して次へ進む（推測で実装しない）
