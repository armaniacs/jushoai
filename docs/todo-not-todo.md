### 6. 半角・全角を強制するページへの対応

- 動機: 欄に `pattern` や placeholder で半角(例: `[0-9]{7}`)や全角(例: `[０-９]{7}`)を強制するページが実在する。半角英数の氏名欄(ローマ字氏名)とカナの表記種別(kanaKind)は既存だが、氏名以外(郵便番号・電話・住所)の全角強制と、欄単位の強制判定は扱っていない。全角を強制する欄では、半角のまま注入するとページ側バリデータに弾かれる可能性がある。
- 範囲: pattern・placeholder・maxlength から欄が求める半角/全角を判定し、注入値を決定的に変換する(数字・英字・カナ)。判定できない欄は現行どおり。
- 注意: 変換は core/ の決定的コードで行い、変換後の値をプレビューで確認できる。既存の kanaKind(ひらがな/全角カナ/半角カナ)と同じ型の拡張。
- 手順: fixture 先行(`tests/core/`)→ core/formatters の変換追加 → planner。

### 7. ハイフン・ダッシュの扱いが特殊なページへの対応

- 動機: ダッシュ系の文字は種類が多い(`-` U+002D、`‐` U+2010、`-` U+2013、`―` U+2014、`―` U+2015、`ー` U+30FC)。ページ側の pattern やバリデータが特定の 1 種しか受け付けないことがあり、プロファイルの住所・建物名に含まれるダッシュの種類が違うと一致しない。電話・郵便番号のハイフン有無の判定は既存だが、それ以外の欄(住所・建物名・氏名)への注入と種類の統一は扱っていない。カナ判定は pattern 内の `U+2015` をカナ範囲に含めており、ダッシュの扱いは分類と整形の両方にまたがる。
- 範囲: pattern・placeholder から求められるダッシュ種別を判定し、注入時に決定的に統一する。分類ではダッシュの種類差異を同一視する(カナ語彙のトークン化と同じ方向)。
- 注意: どの文字を同一視するかは fixture で先に固定する。正規表現のテストが落ちたら期待値ではなく辞書を直す方針に従う。
- 手順: fixture 先行 → core/ のダッシュ語彙テーブル → 分類・整形。

### 8. 長すぎる建物名の略記

- 動機: 建物名は欄の `maxlength`・表示幅を超えやすく、現在は「超過は切り詰めず警告して注入しない」。実際のフォームでは建物名を略して入れるのが一般的な運用であり、警告だけで終わると入力が完了しない。
- 範囲: 建物名が `maxlength`(または表示幅)を超えるとき、決定的な略記規則(例: 半角化・空白と記号の圧縮・接尾語の短縮。採否は設計時に決める)で短くして注入する。略記前の値と略記後の値をプレビューに表示し、承認してから入れる。

- 手順: fixture 先行 → core/ の略記規則 → planner → プレビューの表示。

## NOT-TODO

### 1. 承認なし注入(ページロード時の自動入力・自動入力モード・opt-in も含む)

- なぜ: プレビュー承認は「確認して入れる」という信頼の柱そのもの。分類はルール+AI で完璧ではなく、ページ由来の文言(ラベル・legend・placeholder)による誤判定が常に起き得る(実績: 注意書き文言で漢字氏名欄がカナ欄に誤認、`First name on ID` を人名として誤分類、4 桁市外局番の誤分割)。誤注入を人が止められるのがプレビューである。さらに、悪意あるページの文言で分類を歪めるプロンプト注入の影響は、承認経由では「確認できる事故」で済むが、自動注入では「発見できない事故」になる。opt-in でも信頼の柱をオプションに格下げする。
- 解く条件: 原則なし。「分類の精度が上がったら」は解放条件にならない(誤判定の常在が設計の前提)。唯一の解放条件は、プロダクトの信頼の柱を「確認して入れる」から別のものに置き換える決定をしたとき。その場合は新しい設計書から始める。

### 2. LLM による値の生成・分類の LLM 主体化

- なぜ: 値を LLM に作らせるとプロファイルの値が外部に渡り、2 つ目の柱「外部に送らない」が崩れる。整形(分割・カナ変換・ハイフン・和暦)は決定的でなければテストも品質保証もできない。ルール先頭・信頼度未満だけ AI、という構造は通信量・レイテンシ・コストのすべてを支えており、LLM 主体化はこの 3 つを同時に悪化させる。
- 解く条件: なし。ルール主体は設計の中心であり、AI の役割は補助に留める。

### 3. プロファイルのクラウド同期・サーバー・アカウント(`chrome.storage.sync` を含む)

- なぜ: 「個人情報はブラウザ外に送らない」がプロジェクトの核の約束。`chrome.storage.sync` は手軽だが、プロファイルの値が Google / Microsoft のクラウドに乗るため、プライバシーの文言・ストア説明・AMO の `data_collection_permissions`(`required: ['none']`)の意味を書き換えることになる。サーバーを持つと運用・障害・審査のすべてが変わる。持ち出しの需要は、ユーザー起点のエクスポート/インポート(TODO 3)で足りる。
- 解く条件: 2 つの柱のうち「外部に送らない」を公式に置き換える決定をしたときのみ。その場合も既定はオフで、明示的な同意フローが前提。

### 4. テレメトリ・利用統計の収集

- なぜ: AMO で `data_collection_permissions`(`required: ['none']`)を宣言し、ストア説明も「データを収集しない」で通している。監査ログは端末内 7 日間の設計。テレメトリの追加はこの約束全体を崩し、審査上の優位性(収集なし)を失う。要望は GitHub Issue と `make addurl` による fixture の蓄積で既に受けている。

### 5. 汎用フォームツール化(パスワード・クレジットカード・任意カスタム項目・多言語辞書・法人フル対応)

- なぜ: 日本式フォーム特化を徹底する(2026-10-17 決定)。1Password・Chrome 標準が強い領域との競合は守備範囲外で、勝つ見込みのない戦場に保守コストを払うことになる。任意カスタム項目は分類・プレビュー・設定 UI・テストがすべて倍になる。「多言語対応」も日本のフォームで実際に困る欄という基準から外れる。法人対応は「会社名・部署の text 欄のみ」(TODO 5)に留め、カナ・法人種別まで広げない。

## 設計の不変条件(NOT-TODO の土台)

TODO に着手するときも、以下は変更しない。

- LLM は分類だけを行い、値は作らない。プロファイルの値は外部に送らない
- `core/` は DOM にも LLM にも依存しない純粋関数
- 注入は必ずプレビュー経由(承認してから)。入力済み欄は上書きしない
- 値注入はネイティブ setter 経由(`el.value = ...` に置き換えない)
- UI は Shadow DOM(closed)。ページ由来の文字列は `textContent` で入れる
- 通信は設定で選んだプロバイダのみ、送るのは欄のメタデータのみ
- egress は fail-closed(解決不能なら送らない・保存しない)
