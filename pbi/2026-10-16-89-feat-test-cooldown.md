# PBI: 設定画面の接続テストボタンにクールダウンを付ける

## ユーザーストーリー

API利用料を負担する利用者として、設定画面の接続テストボタンに連打防止のクールダウン（数秒の無効化）がほしい、なぜなら接続テストは単一欄1リクエストで最小だが、連打するとそのまま課金リクエストになるためだ

## 優先度

- 順位: 8位 / 12件
- RICE スコア: 50（Reach=20 / Impact=0.25 / Confidence=50% / Effort=0.05人月）
- 根拠: 金額影響は軽微だが安く防げる。依存なし
- 出典: `plans/2026-10-15-2247-review-1014z.md` FinOps Low 指摘「接続テスト連打の課金（Nice to have）」

## 現状の事実確認（実装者向け前提）

- 接続テスト経路: `src/llm/provider-registry.ts` の `test()` は `TEST_FIELD`（単一欄）に対する `classify([TEST_FIELD])` を1回だけ実行し、`purpose: 'connection-test'` で監査する。すなわちボタン1押下＝課金リクエスト最大1件が事実上の上限である。
- テストボタン経路: `src/entrypoints/options/ai-section.ts` の `buildActionRow` が「接続テスト（保存済みの設定で実行）」ボタンを描画し、`disabled = state.testing` のみで実行中だけ無効化する。`testAiSection` は `if (state.testing) return` のガードはあるが、完了後は即 `state.testing = false` に戻るため、完了直後の連打はそのまま連続リクエストになる。
- 制約: 通常の単発テストの操作性を損なわないこと（単発の応答速度・表示文言は変えない）。

## BDD受け入れシナリオ

```gherkin
Scenario: 接続テスト直後はボタンが数秒無効化される
  Given 設定画面で有効なプロバイダ設定が保存されている
  When 利用者が接続テストボタンを押下して結果が表示される
  Then ボタンは数秒間（例: 3〜5秒）無効化され、押下しても新規リクエストが発生しない
  And クールダウン終了後はボタンが再び押下可能になる

Scenario: 単発テストの操作性は変わらない
  Given 設定画面で有効なプロバイダ設定が保存されている
  When 利用者が接続テストボタンを1回だけ押下する
  Then 従来どおり速やかに「接続テスト中…」→結果（成功/失敗理由）が表示される
  And クールダウン中であることが分かる表示（無効化・残り時間・文言のいずれか）がある

Scenario: 連打しても課金リクエストは増えない
  Given 接続テストの結果が表示された直後である
  When 利用者がクールダウン中にボタンを複数回押下する
  Then バックグラウンドへの `ai-test` 要求は追加で送信されない
```

## 受け入れ基準

- [x] 単発押下では従来どおり1リクエストのみで結果が表示されること
- [x] テスト完了（成功・失敗いずれも）後にボタンが数秒間無効化され、その間の押下で新規リクエストが発生しないこと
- [x] クールダウン終了後にボタンが自動で再有効化されること
- [x] クールダウン中であることが利用者に分かる（disabled・残り秒数・文言のいずれか）こと
- [x] 実行中（`testing` 状態）の既存ガードを壊さないこと

## テスト戦略

### E2Eテスト（最小限）

- 設定画面で接続テストを1回押下→結果表示→数秒無効→再有効化になることの手動確認（`samples/` 対象外のため、実ブラウザでの目視でよい）

### 統合テスト（中程度）

- `ai-section` の描画・通知モック経由で、テスト完了直後のボタン押下が `testAiViaBackground`（`ai-test` 要求）を追加呼出ししないこと

### 単体テスト（多数）

- クールダウン時間定数の境界値（0秒にならない・上限を超えない）
- 成功時・失敗時・バックグラウンド無応答時のいずれでもクールダウンに入ること
- クールダウン満了後に再テストが可能になること
- 実行中二重押下ガード（`state.testing`）が維持されること
