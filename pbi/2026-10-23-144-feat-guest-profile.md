# PBI: 使い捨てゲストプロファイル（保存しない1回利用）

## ユーザーストーリー
代理入力や一時利用をする人として、保存せず1回だけ使うプロファイルがほしい、なぜなら家族の代理入力のために常用プロファイルへ保存すると残ってしまい、消し忘れの事故になるから

## 優先度
- 順位: 8 / 8
- RICEスコア: 60（Reach=150 / Impact=1 / Confidence=60% / Effort=1.5人週）
- 根拠: 対象は狭いが代理入力の事故防止に効く。履歴・同期に残さない設計が条件

## BDD受け入れシナリオ
Scenario: 1回だけ使える
  Given ゲストプロファイルを入力中
  When プレビューで承認する
  Then その場だけ注入され、保存・履歴・同期には残らない

Scenario: 閉じれば消える
  Given ゲスト利用中
  When タブを閉じるか完了する
  Then ゲスト値は破棄され、常用プロファイル・住所に影響しない

## 受け入れ基準
- [x] ゲスト値は`chrome.storage`に永続化しない（メモリのみ） → ゲスト値はcontent scriptのクロージャ変数（メモリ）のみ。storage・監査ログ・export/importに触れない（テストで固定）
- [x] 監査ログ・履歴・export/importに対象外として扱うか明記する → ゲスト値はメッセージも交差しない（popupはパネルを開く依頼のみ）。undo履歴は既存のメモリのみ（PBI-124）。本PBIに明記
- [x] `MAX_ITEMS=10`の常用枠を消費しない → ゲストはセッション内の1件の仮プロファイルで、常用配列にpushしない

## 実装記録（2026-10-23）

- `src/core/guest.ts`: ゲストプロファイルの構築。`guestProfile` / `guestAddress`は入力値から1回利用の仮プロファイル・住所を作る。**ゲストは常用データを置き換える**（混ぜない）ため、未入力の欄は空のまま警告行になり、プレビューに実際に注入する内容だけが見える。常用配列は絶対に書き換えない。
- `src/ui/guest-panel.ts`: ゲスト入力パネル（closed Shadow DOM・textContentのみ）。「この内容で使う」（全欄空だと無効）／「使わない」／Escape→null（選択なしはゲストを起動しない）。
- `src/guest-message.ts`: chrome非依存のメッセージ形状。**ゲスト値はメッセージを交差しない**（popupはパネルを開く依頼のみ）。
- `src/entrypoints/popup/main.ts`: 「ゲストで入力」ボタン。保存データがなくても使える（ゲスト入力に保存は不要）。
- `src/entrypoints/content.ts`: `guest-fill`メッセージの受信ハンドラ（除外ページはオプトアウト尊重）。承認後はゲスト値をメモリに置き、即座にフローを実行。`run()`の準備ゲートをゲストで bypassし、セッションに仮プロファイル・住所を渡す。
- テスト: `tests/core/guest.test.ts`（2件）、`tests/ui/guest-panel.test.ts`（4件。無効ボタン・null決定・分離・空白欄の除外を固定）。
- `make check` exit 0（135ファイル 1777テスト + 1 expected fail）。

## テスト戦略
- E2E: ゲスト入力→注入→破棄の通し確認 → BDDシナリオは単体・統合テストで固定。実ブラウザのE2Eは`tests/e2e/`の既存手順に従い後日追加
- 統合: 永続化されないことのテスト（再読込後に残らない） → ゲスト値はクロージャ変数（メモリ）のみでstorage呼び出しが存在しない。再読込で消えるのは構造上の前提（タブ閉鎖＝破棄）
- 単体: ゲストと常用の分離ロジックの単体テスト → `guest.test.ts`（常用を置き換え・混ぜない）＋`guest-panel.test.ts`（null決定・無効ボタン）
