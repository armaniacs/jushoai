# PBI: 初回向けに架空データのお試し入力を用意する

## ユーザーストーリー
初めて使う人として、架空の名前と住所で試し入力したい、なぜなら自分の本名や住所を入れる前に操作と自動入力を安心して試したいから

## ビジネス価値
- 初回（有効プロファイルなし）の不安を下げ、試用から定着につなげる
- 本物データの入力抵抗を下げ、誤入力・離脱を減らせる
- 測定: 初回バナー表示→お試し入力→保存成功に至る割合

## BDD受け入れシナリオ

```gherkin
Scenario: 初回に両画面でお試し案内が出る
  Given 有効なプロファイルが0件の初回状態
  When プロファイル画面または住所画面を開く
  Then 先頭に初めて向け案内とお試し入力ボタンが表示される

Scenario: お試し入力で空欄だけ埋まる
  Given 初回状態でカードが空
  When お試し入力を押す
  Then 空欄に架空の名前と住所が入り入力済みの値は変わらない
  And 自動保存はされず保存ボタンで確定できる

Scenario: 押すたび別人物になる
  Given 初回状態の空カード
  When お試し入力を繰り返し押す
  Then 毎回異なる架空人物の値が入る

Scenario: カードが0件でもお試し入力できる
  Given プロファイルも住所も0件の状態
  When お試し入力を押す
  Then 各1件のカードが作られて架空値が入り保存ボタンで確定できる

Scenario: 有効データができたら案内は消える
  Given 有効なプロファイルが1件以上ある
  When 設定画面を開く
  Then お試し案内は表示されない
```

## 受け入れ基準
- [ ] 初回＝有効プロファイルなし（`validateProfile` 通過が0件）のときのみ両画面の先頭に案内を出す
- [ ] ボタンは空欄だけ埋め、入力済みを上書きしない。カードが0件の側は1件作って埋める。自動保存しない
- [ ] 生成値は必ず保存検証を通過する（プロファイル・住所とも）
- [ ] 外部送信・永続化なし（入力欄に流すだけ）
- [ ] 依存追加なし（Fakerは使わない）
- [ ] `make check` が緑

## テスト戦略（t_wadaスタイル）

### E2Eテスト
- 初回→お試し→プロファイル保存→住所保存の通し確認（手動）

### 統合テスト
- 初回判定で両画面にバナーが出ること、有効化後に消えること
- 入力済み保持（上書きなし）と未保存（ストレージ不変）の確認

### 単体テスト
- 生成値が `validateProfile`／`validateAddress` を常に通過すること（反復試行含む）
- 連続生成で値が変わること
- セイ・メイが全角カナ、郵便番号7桁、都道府県が正式名称、電話10〜11桁、誕生日が実在日であること

## 実装アプローチ

- **Red-Green-Refactor**: TDDサイクルを各レイヤーで適用

## 実装者向け注記

### 現状コードの確認
（着手前に必ず実行すること）

```bash
grep -rn "EMPTY_PROFILE\|EMPTY_ADDRESS" src/core/types.ts

```

確認済み（2026-10-28）: ダミー生成・Faker・お試しUIはいずれも未実装。`dependencies` は空で純粋関数追加が自然。

### 実装手順
1. 画面シナリオの確認を先に書く（初回バナー表示→お試しで空欄が埋まる→未保存）
2. `src/core/sample-data.ts` に生成関数を作る（名字・名前＋カナ対照表、ローマ字、都道府県は既存表から選択、郵便・電話・メール・誕生日を検証通過形で生成）
3. `tests/core/sample-data.test.ts` で検証通過と多様性を先に失敗させてから通す
4. options の両画面先頭に初回のみ案内＋ボタンを出し、空欄だけ埋めて再描画する（保存は既存の各画面保存に委ねる）
5. `make check` で緑を確認し、初回フローを手動で通す

### 落とし穴
- Fakerを入れないこと（約1MB増・日本語検証の後処理が別途要るため自前と同量になる）
- 名字とカナ・ローマ字の対応を崩さないこと（別々に乱数引きしない）
- 都道府県は自由文字列にせず既存 `PREFECTURES` から選ぶこと
- 電話は数字のみ10〜11桁、郵便番号は数字7桁に整形してから返すこと（`normalize` 任せにしない）
- 初回判定は「カードの空・非空」ではなく「有効プロファイルなし」で行うこと
