# PBI: 繰り返し入力の軽減（サイト別承認記憶＋プレビュー内切替）

## ユーザーストーリー
同じサイトで繰り返し入力する利用者として、毎回のプレビュー承認を短くしたい、なぜなら「ボタン→プレビュー承認→注入」の2段が毎回は面倒だから。ただし自動入力はしないでほしい

## 優先度
- 順位: 5 / 7
- RICEスコア: 200（Reach=500 / Impact=1 / Confidence=80% / Effort=2人週）
- 根拠: 常連の手数削減。自動入力は含めず同意を保つ。依存なし

## BDD受け入れシナリオ
Scenario: 同じ構成では確認が短くなる
  Given 同一サイト・同一欄構成で前回承認済み
  When ボタンを押す
  Then 差分だけ強調した短縮プレビューになり承認後に注入される

Scenario: 構成が変われば通常プレビューに戻る
  Given 欄構成・プロファイルが前回と違う
  When ボタンを押す
  Then フルプレビューで承認を求め自動注入はしない

## 受け入れ基準
- [x] ページ読み込み時の自動入力はしない（MVP除外方針を維持） → ボタン押下→分類→プレビュー承認→注入の順は変えない。短縮プレビューは表示だけの短縮で、注入は常に承認後
- [x] 記憶は端末内のみで外部送信しない → 承認記録は`chrome.storage.local`に欄ごとのダイジェスト（field id・status・displayのdjb2ハッシュ）だけを保存。生のプロファイル値・ラベルは保存・送信しない（テストで固定）
- [x] 除外URL登録サイトでは記憶を使わずボタンを出さない → 除外ページはセッションが`excluded`を返しパネルを開かない。承認記憶の読み書きもパネル経由のみ

## 実装記録（2026-10-23）

- `src/core/site-approval.ts`: 承認記録の純粋層。`recordFor`（host＋フォーム署名＋選択中プロファイル/住所＋欄ごとのダイジェスト）、`matches`（同一サイト・同一欄構成・同一選択のときだけ短縮）、`changedRows`（記録とダイジェストが違う欄だけ残す。欄idのない行は触らない）。`digest`はdjb2の32bitハッシュ。
- `src/approval-store.ts`: `chrome.storage.local`の`jushoai:site-approvals`（host→記録）。壊れた・手編集の値は空マップとして読む。生値は保存しない。
- `src/ui/preview.ts`: 「前回と同じ欄を表示」ボタン（短縮プレビューのときだけ出る。押すと全行に戻る1回だけの展開）。
- `src/content/preview-bind.ts`: 一致する記録があるときだけ差分行＋「N件を前回の承認どおりに入力します」の合成行に短縮。プラン自体は短縮しない（注入は常に全プラン）。クリーン適用後に`recordApproval`で記録。
- `src/entrypoints/content.ts`: 実行ごとにhostの記録を読み、一致するときだけ短縮を渡す。記録は適用後にupsert保存。
- テスト: `tests/core/site-approval.test.ts`（5件）、`tests/approval-store.test.ts`（2件）。
- `make check` exit 0（140ファイル 1794テスト + 1 expected fail）。

## テスト戦略
- E2E: 同一サイト2回目→短縮、構成変更→フルに戻る確認 → 実ブラウザのE2Eは`tests/e2e/`の既存手順に従い後日追加。単体・統合テストで差分ロジックと短縮の条件を固定

- 単体: 差分強調ロジックの単体テスト → `site-approval.test.ts`（`changedRows`・`matches`・ダイジェストの安定性）
