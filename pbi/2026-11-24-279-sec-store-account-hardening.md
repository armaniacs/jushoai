# PBI: ストア提出経路の資格情報を守り、侵害時の手順を用意する

## ユーザーストーリー
拡張の利用者として、配布元のアカウントが乗っ取られても悪性の更新が届かないこと、届いても速やかに止まることを望む、なぜなら拡張は全サイトの入力欄に触れる権限で自動更新されるから

## 区分
将来構想（セキュリティ） / 1.0 後・相当先（大半はユーザー作業）

## 優先度
- 順位: 17 / 17
- RICEスコア: 500 (Reach=100 / Impact=3 / Confidence=50% / Effort=0.3人週。採点は参考値として残す)
- 根拠: 拡張の乗っ取りは利用者全員への影響が最大の事故。`release.yml` は Chrome サービスアカウント鍵・Edge API キー・AMO JWT を `release` environment で扱う。Confidence が低いのは現状の 2FA・保護設定がリポジトリから見えないため
- 判断: 2026-11-24 にユーザー判断で 1.0 必須から将来構想へ移した。着手は相当先とし、RICE では順位を決めない（最後尾に置く）

## BDD受け入れシナリオ

```gherkin
Scenario: タグを打っただけでは提出されない
  Given 誰かが v* タグを push した
  When  Release ワークフローが submit に到達する
  Then  release environment の承認者が承認するまで提出は止まる

Scenario: 鍵が漏れたときに手順どおり止められる
  Given ストア資格情報の漏洩が疑われる
  When  保守者が runbook を開く
  Then  各ストアでの公開停止・鍵失効・再発行・利用者告知の手順と連絡先が順に書かれている
```

## 受け入れ基準
- [ ] Chrome / Edge / AMO / GitHub の各アカウントで 2FA（可能ならパスキー）を有効化（ユーザー作業・チェックのみ記録し値は書かない）
- [ ] `release` environment に required reviewers と、タグ保護（`v*` の作成を保守者に限定）を設定（ユーザー作業）
- [ ] Chrome サービスアカウント鍵と Edge API キーの更新周期と期限を決め、次回期限を記録
- [ ] `docs/release.md` にインシデント runbook 節を追加（公開停止、鍵失効、修正版の緊急提出、GitHub Security Advisory での告知）
- [ ] Chrome Web Store の「信頼できるテスター／段階的公開」の利用可否を確認し、1.0 で使うか判断を記録
