# PBI: 正式版前に脆弱性スキャンをやり直し、前回指摘の修正を検証する

## ユーザーストーリー
利用者として、正式版がその時点のコードで脆弱性検査を受けていてほしい、なぜなら前回の全体スキャン (2026-10-23) の後に、役割別プロファイル・ゲスト入力・引継ぎ・フォームからの取り込み・除外クイック登録など、ページ由来の入力を扱う経路が大きく増えたから

## 区分
セキュリティ / 1.0 必須

## 優先度
- 順位: 6 / 17
- RICEスコア: 160 (Reach=100 / Impact=2 / Confidence=80% / Effort=1人週)
- 根拠: 工数は大きいが正式版の前提。282 の統合が終わった main を対象にしないと結果が陳腐化するため、統合後に実施する

## BDD受け入れシナリオ

```gherkin
Scenario: 統合後の main を全体スキャンする
  Given 1.0 候補のコミットが main にある
  When  全体スキャン（入力源の列挙 → sink 追跡 → 実行可能な PoC）を行う
  Then  指摘ごとに深刻度・再現手順・修正方針が記録され、High 以上は 1.0 前に修正される

Scenario: 前回の指摘が退行していない
  Given 2026-10-10 と 2026-10-23 のスキャン結果がある
  When  各指摘を現行コードで検証する
  Then  指摘ごとに「修正済み / 受容 / 再発」が判定され、再発は修正 PBI になる
```

## 受け入れ基準
- [ ] 重点対象を明記してスキャン: ページ由来文字列の Shadow DOM 描画（`textContent` 徹底）、runtime メッセージの sender 検証と型ガード、`IMPORT_DRAFT` の値取り込み、ゲスト・引継ぎのタブ内メモリ、監査ログの TSV 書き出し（CSV/TSV インジェクション）、`validateBaseUrl` と DNS rebinding、API キーの復号境界、pattern 属性の ReDoS
- [ ] 前回結果の各指摘に判定を付ける（vulnhunt-fix-verify 相当）
- [ ] High 以上は修正し、修正ごとに失敗するテストを先に置く
- [ ] スキャン成果物は従来どおり sources zip から除外されていることを確認（テスト鍵を含むため）
- [ ] 結果の要約（指摘数と処置）を CHANGELOG の 1.0.0 節に載せるか判断を記録
