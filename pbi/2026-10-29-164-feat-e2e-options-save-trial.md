# PBI: 設定画面の保存分離とお試し入力にE2Eを追加する

## ユーザーストーリー
開発者として、保存分離とお試し入力の実ブラウザ回帰がほしい、なぜなら0件試し入力のような導線破綻は単体テストの届かない範囲で起きるから

## ビジネス価値
- 手動ウォークスルーの自動化により、設定画面の回帰を早期検出できる
- 測定: `make e2e-chrome` / `make e2e-firefox` の緑維持

## BDD受け入れシナリオ

```gherkin
Scenario: プロファイルだけ保存できる
  Given 有効なプロファイル1件と住所0件の保存状態
  When プロファイル画面で保存を押す
  Then 保存成功が表示され住所エラーは出ない

Scenario: お試しから保存まで通る
  Given プロファイルも住所も0件の保存状態
  When お試し入力を押して保存を押す
  Then カードが作られて保存が成功する

Scenario: 最終削除から復帰できる
  Given 保存済みの試しデータがある状態
  When 最後のプロファイルを削除し再度お試し入力して保存する
  Then 0件を経て保存が成功する
```

## 実装アプローチ
- **Outside-In**: 既存ハーネス（設定画面の直接操作・ストレージ書き込み）の流用
- 値はアサートしない（生成値はランダム）。件数と通知文だけ見る

## 見積もり
3 （要チームでの見積もり）

## 技術的考慮事項
- 依存関係: なし。新規ヘルパーは各e2eファイル内に置く
- Chromeは `chrome-extension://` 直アクセス、Firefoxは chrome コンテキストのタブ方式に従う
- 保存ボタンは `#profiles` / `#addresses` 配下に絞る（非表示側の同名ボタンを踏まない）

## 実装者向け注記

### 現状コードの確認
```bash
grep -n "settings page" tests/e2e/chrome.e2e.ts tests/e2e/firefox.e2e.ts
```

確認済み（2026-10-29）: E2Eはfill系と従来設定系のみ。新規3フローは未カバー。

### 実装手順
1. Chrome側にヘルパーと3テストを追加し `HEADLESS=1 E2E_NO_SANDBOX=1 make e2e-chrome` で緑を確認する
2. Firefox側に同型を追加する（実行はユーザーの端末で）
3. コミットしてPRに記録する

### 落とし穴
- 保存ボタンは両ページに同名で存在するため xpath を節に絞ること
- 試し入力の成功表示と保存成功表示は同じ `p.saved` のため、文言が変わるまで待つこと
- ストレージはテスト間で引き継がれるため各テスト先頭で明示的に seed すること
