# PBI: プロファイルの値をパスフレーズで暗号化して保存できるようにする（任意）

## ユーザーストーリー
共用 PC や管理されていない端末を使う利用者として、登録した氏名・住所・電話番号を暗号化して保存したい、なぜなら今はブラウザのプロファイルを読める人なら誰でも平文で読めるから

## 区分
将来機能（セキュリティ） / 1.0 後

## 優先度
- 順位: 13 / 17
- RICEスコア: 4 (Reach=10 / Impact=2 / Confidence=50% / Effort=2.5人週)
- 根拠: 鍵を端末内に置く限り、同じ端末のマルウェアには効かない（API キーの暗号化と同じ限界）。効くのはストレージだけの流出や共用端末で、パスフレーズ入力の手間が「1 クリック」の価値とぶつかる。280 で限界を明示したうえで需要を待つ
- 着手条件: 共用端末での利用や暗号化保存の要望が Issue で観測されたら着手段階を確認する

## BDD受け入れシナリオ

```gherkin
Scenario: 暗号化を有効にするとロックが掛かる
  Given 利用者が設定で「パスフレーズで保護する」を有効にした
  When  ブラウザを再起動して「JushoAI で入力」を押す
  Then  パスフレーズ入力を求められ、解錠するまでプロファイルの値は読み出されない

Scenario: パスフレーズを忘れた
  Given 利用者がパスフレーズを忘れた
  When  「保護を解除してデータを消す」を選ぶ
  Then  暗号化されたプロファイルは削除され、復元できないことが事前に明示されている
```

## 受け入れ基準
- [ ] 鍵導出（PBKDF2 か Argon2 相当。WebCrypto で使えるもの）と AES-GCM、解錠状態の保持範囲（セッション内のみ）を設計書に書く
- [ ] 解錠前の content script には値を渡さない
- [ ] JSON エクスポートの暗号化有無を選べる
- [ ] ゲスト入力・引継ぎとの関係を整理する

## テスト戦略
- E2E: 有効化 → 再起動 → 解錠 → 入力
- 統合: 解錠前のメッセージ応答に値が含まれない
- 単体: 鍵導出・暗号化・誤パスフレーズ
