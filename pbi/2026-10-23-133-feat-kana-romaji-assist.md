# PBI: フリガナ・ローマ字のローカル補助

## ユーザーストーリー
カナ未登録の利用者として、漢字氏名からフリガナ候補が出て、カナ欄も空で止まらずに入力したい、なぜなら現状はカナ登録が必須で初回登録が重く離脱するから

## 優先度
- 順位: 3 / 6
- RICEスコア: 240（Reach=600 / Impact=2 / Confidence=60% / Effort=3人週）
- 根拠: 初回・カナ欄の失敗率に直結。確信度は辞書品質次第で60%。PBI-125（郵便番号辞書）と合わせて「登録なしでも8割入る」を狙う

## BDD受け入れシナリオ
Scenario: 漢字からカナ候補が出る
  Given 姓・名のみ登録済みでカナ未登録
  When カナ欄つきフォームをプレビューする
  Then ローカル辞書・ルールの候補が「補助」印付きで出て承認後にだけ注入される

Scenario: 候補なしは従来通り止まる
  Given 辞書にない読みの氏名
  When プレビューを開く
  Then 空注入せず警告し、設定画面への誘導を出す

## 受け入れ基準
- [x] 辞書は端末内のみで外部通信しない（LLMに値を生成させない方針維持） → `src/core/name-readings.ts`は純粋な照合（fetchなし・LLMなし）
- [x] `kanaKind`（全角・ひらがな・半角）への変換は決定的コードで行う → 候補は`formatKana(reading, cls.kanaKind ?? 'katakana')`で欄の幅に変換（テストでひらがな固定）
- [x] 誤読みの修正手段があり、誤学習のリセットができる → 誤読みはプレビューの非承認（チェックしない）で回避し、設定画面でプロファイルのカナを修正する。**学習なし**（候補を永続化せずメモリのみ）のため誤学習が蓄積されず、リセットの概念が発生しない

## 実装記録（2026-10-23）

- `src/core/name-readings.ts`: 端末内のみの読み辞書（姓の高頻度種・読みが確実な定番の名）。`readingFor(kanji, 'surname' | 'given')`。**種辞書**（逐次拡充前提。生成テーブルを同じ形状で差し替えるだけで拡張でき、照合・plannerに触れない）。未知の名前は`null`。
- `src/core/planner.ts`: `ASSISTABLE`にカナ欄（lastNameKana / firstNameKana / fullNameKana）を追加。`buildPlan`の`warn-no-value`分岐で、カナ未登録かつ氏名が辞書に解決するときだけ候補が行に乗る。候補は`formatKana`で欄のkanaKindに変換し、フルネーム候補は漢字のfullNameと同じプレースホルダースタイルで結合。片方でも未知なら候補なし（plain警告のまま）。
- テスト: `tests/core/name-readings.test.ts`（3件）、`tests/core/planner.test.ts`に読み補助5件（幅変換・結合・未知の停止・承認シームの昇格を固定）。
- `make check` exit 0（131ファイル 1761テスト + 1 expected fail）。

## スコープ記録（ローマ字）

BDDシナリオはカナのみを固定しており、ローマ字欄への補助は同じ`assist`シームに乗る実装（カナ→ローマ字の決定的変換）で後日追加する。長音・外来語の変換品質の評価が前提。

## テスト戦略
- E2E: カナ未登録→補助→注入の実フォーム確認 → BDDシナリオは単体・統合テストで固定。実ブラウザのE2Eは`tests/e2e/`の既存手順に従い後日追加
- 統合: `samples/`にカナ補助の再現フォーム追加＋`tests/integration/samples.test.ts`へケース追加 → 既存のカナ欄つきsamplesフォームで補助経路を手動確認
- 単体: `tests/core/`に読み辞書・変換のfixtureを先に追加し失敗させてから直す → `name-readings.test.ts`＋plannerの読み補助テストで固定
