# PBI: 脅威モデルを文書化し、端末に残るデータの扱いを利用者に明示する

## ユーザーストーリー
個人情報を登録する利用者として、何が端末のどこにどの形で残り、何から守られて何から守られないかを知りたい、なぜなら API キーは暗号化されると書かれている一方、プロファイルの値がどう保存されるかは明示されておらず、安全性を過大に受け取りかねないから

## 区分
セキュリティ / 1.0 推奨

## 優先度
- 順位: 8 / 17
- RICEスコア: 120 (Reach=60 / Impact=1 / Confidence=80% / Effort=0.4人週)
- 根拠: プロファイルと住所は `chrome.storage.local` に平文で置かれる（API キーのみ AES-GCM エンベロープ）。監査ログは AI に送った内容（ページ由来の label など）を 7 日間平文で保持する。どちらも設計として妥当だが、利用者向けの説明と保守者向けの前提が 1 か所にまとまっていない。276 の重点対象を決める材料にもなる

## BDD受け入れシナリオ

```gherkin
Scenario: 利用者が端末に残るデータを確認できる
  Given 利用者がプライバシーのガイドを開く
  When  「端末に保存されるもの」の節を読む
  Then  プロファイル・住所・覚えた対応付け・監査ログ・API キーのそれぞれについて、保存場所・暗号化の有無・保持期間・消し方が書かれている

Scenario: 保守者が守る範囲と守らない範囲を確認できる
  Given 保守者が設計書の脅威モデル節を開く
  When  攻撃者の種類ごとの行を読む
  Then  悪意あるページ・悪意ある AI 応答・同じ端末の他の利用者・端末のマルウェア・配布経路の侵害について、対策と受容した限界が書かれている
```

## 実装記録

- 表の置き場所: 新規 `docs/superpowers/specs/2026-11-24-threat-model.md` を作成した。既存設計書への追記ではなく新規 spec にした理由は、対象が横断的な前提整理であり既存の個別設計書のどれにも属さないため。軸は資産 × 攻撃者（悪意あるページ、悪意ある AI 応答、同じ端末の他の利用者、端末のマルウェア、配布経路の侵害） × 対策 × 受容した限界とし、信頼境界と資産一覧（保存場所・暗号化・保持期間・消し方・外部送信）も同ファイルに置いた。受容限界は `SECURITY.md` の「対象外の例」と整合させた
- 拡充した節: `site/content/ja/privacy.md` と `site/content/en/privacy.md` の「端末内だけに保存・保持するデータ」（既存節の拡充。新規 H2 は足さず、日英の H2 数・リンクに変更なし）と「監査ログ」（架空値の記録例と、ページ由来の文言に個人情報が含まれうる点を追加）。プロファイル・住所の値は暗号化されない（平文）ことを両言語で明記した。safety ガイドは既存の「タブの中だけに置く一時データ」「API キーと権限」と privacy への誘導で足りているため、新規節は足さず構造を変えなかった
- 開示欄の一致確認の結果: `docs/store-listing.md` の「データ使用の申告」（個人を特定できる情報はチェックしない、認証に関する情報とウェブサイトのコンテンツは AI を使う設定のときだけチェック）と Firefox の `data_collection_permissions`（必須 `none`、任意 `websiteContent`）は、資産表および privacy ガイドの記述と一致する。不一致はないため文書側の修正は不要で、ストア側の変更作業も発生しない
- BDD 確認手順: シナリオ 1 は privacy ガイド（日英）の拡充節を目視し、5 資産（プロファイル、住所、覚えた対応付け、監査ログ、API キー。監査ログと API キーは節末の誘導先に記載）ごとに保存場所・暗号化の有無・保持期間・消し方が書かれていることを確認した。シナリオ 2 は新規 spec の攻撃者別の表に 5 攻撃者の対策と受容限界が書かれていることを確認した
