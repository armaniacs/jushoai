# PBI: 設定ナビに登録件数を表示する

## ユーザーストーリー
設定画面の利用者として、各項目の登録件数をナビで見たい、なぜなら何が何件入っているかを一目で把握したいから

## 優先度
- 順位: 1 / 1
- RICEスコア: 約21（Reach=2 / Impact=2 / Confidence=80% / Effort=0.15人月）
- 根拠: 単一候補。依存なし（既存storeの読み取りのみ）

## ビジネス価値
登録状況の可視化により、未登録への気づきと初回ガイドへの連携が強まる

## BDD受け入れシナリオ

```gherkin
Scenario: 各項目に件数が出る
  Given プロファイル2件・住所1件・除外URL3件・対応付け1件・監査ログ5件の保存状態
  When 設定画面を開く
  Then ナビにプロファイル (2)・住所 (1)・起動しないURL (3)・覚えた対応付け (1)・通信の監査ログ (5) と出る

Scenario: 0件も0と出る
  Given 住所0件の保存状態
  When 設定画面を開く
  Then 住所 (0) と出る（非表示にしない。0こそ行動の合図のため）
```

## 受け入れ基準
- [x] 対象5項目（プロファイル・住所・起動しないURL・覚えた対応付け・通信の監査ログ）に件数が出る。AI判定は対象外
- [x] 件数は保存済みの登録総数（監査ログは現entries件数）
- [x] 追加・削除・保存・取り込みのたびに件数が更新される
- [x] `make check` が緑

## テスト戦略
- E2E: 設定画面で件数表示と保存後の更新を確認
- 統合: 各store読み取りと表示の結合テスト
- 単体: バッジ描画、0件表示、上限値（10件）の境界テスト

## 実装アプローチ
- **Outside-In**: ナビ表示の受け入れテストから開始し、失敗を確認してから実装
- ナビ組み立て（`nav.ts`）に件数更新関数を足し、各セクションの描画・保存後に呼ぶ

## 見積もり
3 （要チームでの見積もり）

## 技術的考慮事項
- 依存関係: なし。読み取りは `loadData`・`loadExcludedUrls`・`loadMappings`・監査 state 読み取りの既存経路を使う
- 件数取得の失敗時はバッジを出さずラベルのみ（保存系の成否に影響させない）
