# PBI: 監査ログ sizeCache の変異前提の文書化

## ユーザーストーリー

保守担当者として、監査ログのサイズ計測キャッシュ（`sizeCache`）の変異前提が文書化されてほしい、なぜなら entry 改変後に陳腐化した計測値を使い続けるとバイト予算の判定がずれる恐れがあり、責任範囲を曖昧なままにしたくないから。

## 背景・現状確認

- 対象: `src/ai/audit-log.ts:110-117` の `WeakMap<AuditEntry, number>` キャッシュ（`entryBytes`）。
- 現状は `appendEntry` / `pruneEntries` が非破壊（スプレッド・`slice`・`filter` で新配列を返す）で安全に運用されており、既知のバグ報告はない。
- ただし `AuditEntry` は `readonly` / `freeze` ではなく、`batchBytes` は公開関数として外部から可変オブジェクトを受け取れるため、「改変しない前提」がコード上明示されていない。
- 本 PBI は動作変更ではなく、前提の文書化（コメント 1 行規模）または型の `readonly` 化検討に留める。実装コードは書かない。

## 実装者向け注記

### 方向性

- 本命は「mutate しない前提のコメント 1 行」の追加。例として `sizeCache` 定義近傍に entry 改変後の陳腐化と再計測責任を 1 行で残す。
- 代替案として `AuditEntry` の型の `readonly` 化も検討可能だが、本 PBI の範囲では検討に留め、破壊的変更になる場合は別 PBI に分割すること。
- いずれの場合も `entryBytes` / `batchBytes` / `withinByteBudget` の計測ロジック自体は変更しない。

### 現状コードの確認（着手前に必ず実行すること）

```bash
grep -rn "sizeCache\|entryBytes\|batchBytes" src/
```

- `appendEntry` / `pruneEntries` が非破壊であること、`AuditStore.record()` が storage 経由で identity を作り直す旨の既存コメント（102-109 行付近）と矛盾しない表現にすること。
- #6（52）の対応済み内容を先に確認し、コメント位置・文言の重複を避けること。

### 落とし穴

- `WeakMap` のキー identity に依存した最適化であるため、「キャッシュ削除」ではなく「前提の明文化」が目的であることを忘れないこと。
- 過剰な `readonly` 化や `freeze` 導入は API 変更になるため、本 PBI では行わない。必要と判断したら別 PBI として切り出すこと。
