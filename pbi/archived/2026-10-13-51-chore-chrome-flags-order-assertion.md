# PBI: chrome-flags の順序固定 toEqual アサーションを緩和する

## ユーザーストーリー

E2E 基盤の保守担当者として、Chrome 起動フラグのアサーションが順序に依存しない形になってほしい、なぜなら Chrome のフラグ解釈上順序は無意味であり、将来のフラグ追加で不要なテスト破損を起こしたくないから。

## 背景・課題

`tests/e2e/chrome-flags.test.ts:34-44` の `keeps the expected set and order for combined envs` が `toEqual([...])` で順序まで固定している。

- Chrome のコマンドライン引数の解釈上、フラグの順序は意味を持たない。
- 将来フラグを1つ追加しただけでこのテストが落ちる（脆い）。
- 同ファイルの他のケース（`toContain` / `not.toContain` 中心）は集合ベースで書かれており、この1ケースだけが過剰に厳しい。

対象コード（現状確認済み、実装は変更しない）:

- `tests/e2e/chrome-flags.test.ts:34-44`
- 関連: `tests/e2e/chrome-flags.test.ts:7-9`、`27-32` も `toEqual` を使用しているが、本 PBI の対象は `34-44` の複合 env ケースのみとする。

### 実装手順

1. `tests/e2e/chrome-flags.test.ts:34-44` を読み、現在の `toEqual` が順序まで固定していることを確認する
2. アサーションを集合ベースに緩和する（方向性のみ。詳細は実装時に選択）:
   - 方向A（推奨）: `arrayContaining` + 長さ検査の組み合わせへ緩和し、順序非依存かつ余剰検出可能にする
   - 方向B: 順序が仕様として意図的であることが判明した場合は、テストを緩和せずコード側（`chromeLaunchArgs` のコメント等）に順序が仕様である旨を明記する
3. 順序入れ替え・将来フラグ追加を想定した手元検証を行い、不要な破損が起きないことを確認する

### 落とし穴

- 単なる `toContain` の羅列にすると余剰フラグを見逃すため、必ず長さ（または余剰検出の仕組み）と組み合わせること
