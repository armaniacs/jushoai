## 重要指摘事項（優先度順）

### [Medium] 🎯 lastFailureReason が記録のみで本番コードから消費されていない
- 指摘者: System Architect、SRE/Ops Specialist、Domain Logic Expert
- 場所: src/llm/background-gateway.ts:53
- 影響: ClassifyFailure の閉じた語彙を整備したのに理由が可変フィールドに溜まるだけで、content 側は LLM 失敗とルール単独動作を区別できない。auth（要設定修正）と network（再試行可）の切り分けが UI に出ず誤った対処を誘う
- 対処: `classifyAll` か content 側で理由を読んでボタン状態・プレビュー警告に反映する（粗い区分のみ表示し生ステータスは出さない）

### [Medium] 🎯 dispatch 表が呼び出しごとに約21クロージャを再生成し無名で追跡困難
- 指摘者: System Architect、Tuning Expert、Maintainability Guardian
- 場所: src/core/classify-rules.ts（dispatch 配列構築箇所）
- 影響: 60欄で約1200個の使い捨て確保がホットパスに乗る。無名のためスタックトレースでヒットルールが判別できず個別テストも不可。own/legend の 0.7/0.65 ペアは重複で表が実質2倍
- 対処: 表をモジュール定数に昇格し `(m, ownText, legendText) => Classification | null` の名前付き matcher 化。own/legend ペアはデータ行に畳む

### [Medium] 🎯 ID生成経路が二系統に分裂しフォールバックが移行時にしか効かない
- 指摘者: Legacy Bridge Architect、Data Integrity Expert（Blue Team・Red Team も Low で同根指摘）
- 場所: src/storage.ts:59（`newId`）、src/entrypoints/options/main.ts:181,193,225,280,283
- 影響: `crypto.randomUUID` 非搭載環境で移行は成功するのに設定ページの追加・複製5箇所が例外で死ぬ。`newId` 非 export のため今後の呼び出しも直呼びを繰り返す構造
- 対処: `newId` を export して options 側5箇所を一本化する

### [Medium] createAiSectionState が `undefined as unknown as AiSettings` で型を偽装
- 指摘者: Refactoring Evangelist、Maintainability Guardian
- 場所: src/entrypoints/options/ai-section.ts:61
- 影響: `loadPublicAiSettings().then` 前に参照すると実行時エラーになるのに型上は安全に見え、将来の編集者が誤読する
- 対処: `settings: AiSettings | null` にして render 側で早期リターンする

### [Medium] ownerSelect がモジュールグローバル state に暗黙依存し export で公開された
- 指摘者: Maintainability Guardian（Refactoring Evangelist も Low で同根指摘）
- 場所: src/entrypoints/options/main.ts:82
- 影響: 兄弟 builder が純粋なのに対し ownerSelect だけ暗黙依存を持ち、公開 API 化で結合度が上がる。未初期化 state での呼び出しは実行時エラーの原因になる
- 対処: `ownerSelect(value, onChange, profiles)` と引数化し呼び出し側で `state.profiles` を渡す

### [Medium] 旧形式 `{ok:false}`（reason なし）が新 gateway で `bad-response` に誤分類される
- 指摘者: Legacy Bridge Architect
- 場所: src/messages.ts:117（`parseClassifyResult`）、src/llm/background-gateway.ts:70
- 影響: 更新直後の新旧混在期に設定不備・権限不足が「応答不正」として記録され原因切り分けを誤らせる
- 対処: `parsed === null`（旧形式・不明）と `parsed.ok === false`（理由付き失敗）を区別し、前者は理由不明扱いにする

### [Medium] 🎯 フィードバック報告の本文に未クリップのメタデータJSONとフルパスが含まれ公開issueへ送られる
- 指摘者: Red Team Leader（Compliance & Privacy Guard も Low で nearby・sanitizePageUrl を指摘）
- 場所: src/feedback/issue-url.ts:29-33,60-73、src/feedback/issue-url.ts:20-27
- 影響: `META_CLIP_LENGTH` 集約は表示行だけで JSON ブロックは全文出力。`nearby` はページ由来で個人を特定しうる文言を含みうる。`sanitizePageUrl` は pathname を残すためパス埋め込み ID も公開 issue に入る。同意文言だけでは中身を確認できない
- 対処: JSON 側の各文字列にもクリップ適用、URL は host までに縮小、同意文言に含まれる旨を明示する

### [Medium] 🎯 ポップアップのエラー通知に視覚的区別がなくスクリーンリーダーにも伝わらない
- 指摘者: UI Expert、Accessibility Advocate
- 場所: src/entrypoints/popup/main.ts:111-113、src/entrypoints/popup/index.html
- 影響: 3分岐に整理された通知が素の `<p>` のままで視認性が低く、`role="status"` がないため SR 利用者は非同期の分析失敗に気づけない
- 対処: `.notice` にエラー色と余白を付け、notice 生成時に `role="status"` を付与する

### [Medium] 🎯 README.md の読み分け案内に README.en.md の対訳がない

### [Medium] runTest が `unavailable` を `network` に潰す（契約の情報損失）

### [Medium] 🎯 逐次チャンク送信の最長待機がMV3 Service Workerの寿命と綱引きになる
