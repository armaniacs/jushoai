# なぜなぜ分析 — PBI-246 messages.ts 語彙分割の移設先決定 (2026-11-21)

- 手法: 10 質問項目 × 3 立場 (利用者 / 保守担当者 / 開発運用) = 30 本のなぜ連鎖 (PBI-213 実装記録と同形式)
- 挑戦する仮定: 「失敗語彙・表示定数が messages.ts に住み、8 module が wire 経由で失敗語彙を import するのは正常である」
- 候補: **A)** src/core/classifier-failures.ts 新設 / **B)** src/core/classifier.ts に同居 / **C)** src/llm/ 側に置く
- 事実ベース: src/messages.ts 358 行・export 36・importer 25・失敗語彙消費者 8 module・META_CLIP_LENGTH 消費者 (llm/prompt.ts, feedback/issue-url.ts)・core/classifier.ts の「message 語彙を core に持ち込まない」コメント・PBI-46 (wire codec) / 54 (wire vocabulary single) / 175 (wire キー規約) / 190 (decode 表駆動) の履歴

## 利用者の立場

### U1: なぜ分類に失敗した欄の扱いがプロバイダ間で一貫しているのか
なぜ1: 失敗応答が単一の語彙 (ClassifyFailure) に畳まれているから
なぜ2: プロバイダごとの失敗差分を fold する群が 1 箇所にあるから
なぜ3: プロバイダ差分が UI 表示を壊した過去があり、mapFailure 系で一本化したから
なぜ4: 失敗は「1 つの意味論・複数の供給源 (組み込み・OpenAI 互換・Gemini)」だから
根因: 失敗語彙の所有者は 1 箇所でよい — 所有位置の移設はこの一貫性を壊さない形で行うべき

### U2: なぜ失敗時の表示文言が欄ごとに安定しているのか
なぜ1: 失敗語彙から UI 文言への写像が UI 側で統一されているから
なぜ2: 語彙自体は UI に依存せず、意味だけを運んでいるから
なぜ3: 語彙が wire payload として設計されたから
根因: 語彙は「意味」であって「運搬」ではない — 運搬層 (messages.ts) に住む必然がない

### U3: なぜ AI 送信欄の集合がゲートと一致するのか
なぜ1: egress ゲートが送信集合を決め、pipeline が同じ集合を送るから
なぜ2: 失敗が起きたときの再試行・スキップ判断も同じ語彙で行われるから
なぜ3: 失敗語彙が分類パイプラインの意思決定に使われているから
根因: 失敗語彙は分類パイプラインの部品であって、wire の部品ではない

### U4: なぜプロバイダを切り替えても失敗の扱いが壊れないのか
なぜ1: provider-registry が各プロバイダの応答を共通語彙に折り畳むから
なぜ2: 折り畳み先の語彙が供給源非依存に設計されているから
なぜ3: 語彙の定義がプロバイダ実装から分離されているから
根因: 語彙は供給源 (llm 実装) から独立している — 依存の向きは「実装が語彙を参照」であるべきで、語彙が llm 配下にあるのは逆

### U5: なぜ障害時も拡張が動き続けるのか
なぜ1: 分類失敗がルール分類へのフォールバックで吸収されるから
なぜ2: フォールバック判断が失敗語彙の種類 (認証系・形式系・その他) に基づくから
なぜ3: 種類の区別が語彙で安定しているから
根因: 失敗語彙は障害耐性の根幹 — 変更コストが高い場所 (wire 経由の混住) に置くと耐性改善が遅れる

### U6: なぜ摘要・フィードバックの文字数に上限があるのか
なぜ1: META_CLIP_LENGTH が clip 幅を決めているから
なぜ2: clip を使う側 (prompt / feedback) と表示側が同じ幅を参照するから
なぜ3: 定数が共通参照できる場所に置かれているから
根因: clip 幅は wire の約束事ではなく prompt・feedback の約束事 — messages.ts に置く必然がない

### U7: なぜ語彙の追加が表示にすぐ反映されるのか (変更の速さ)
なぜ1: 語彙 → UI 文言の経路が短いから
なぜ2: 語彙の変更が wire 契約変更として誤認されると、不要な慎重化 (別 PBI 扱い) が入るから
なぜ3: 語彙と wire 契約が同じ file に住んでいるから
根因: 語彙と wire の同居が「変更コストの誤認」を生む — 分離が速度を取り戻す

### U8: なぜ失敗理由に欄の中身 (値) が含まれないのか
なぜ1: 語彙が欄メタデータの送信規約 (egress) と別管理だから
なぜ2: 失敗語彙は識別子と種類だけを運ぶから
なぜ3: 語彙の定義者が privacy 境界を意識して分離したから
根因: 語彙を専用 module に分離すると privacy 境界が明示的になる (wire 経由の現状では境界が読み取りにくい)

### U9: なぜ語彙変更で表示が崩れないのか (回帰耐性)
なぜ1: 語彙 fold 群の pin テストがあるから
なぜ2: pin が語彙 module 直下ではなく wire 系テストに混ざっているから
なぜ3: 語彙のテストが運搬のテストと同居しているから
根因: 語彙のテストの所在が運搬層に引きずられている — 移設でテストの所在も正しい層に揃う

### U10: なぜ拡張の更新で破壊的変更が起きにくいのか
なぜ1: wire 形式が版管理されているから (PBI-175/190)
なぜ2: wire 契約の変更は別 PBI という規約があるから
なぜ3: その規約の存在理由は、wire に触る変更が影響広域だから
根因: 「wire に触る = 広域影響」の規約があるからこそ、語彙のような狭域変更を wire file から出す価値が大きい

## 保守担当者の立場

### M1: なぜ失敗語彙が messages.ts に住んでいるのか
なぜ1: 失敗は wire で運ばれる payload だから
なぜ2: wire 実装時に payload 型を messages.ts に定義したから
なぜ3: payload 型と失敗語彙の区別が当時なかったから
根因: 「運搬経路と意味を同じ file が所有した」のが始まり — 運搬と意味の分離が移設の本質

### M2: なぜ 8 module が wire 経由で失敗語彙を import するのか
なぜ1: 失敗語彙の唯一の出口が messages.ts だから
なぜ2: 語彙の本来の出口 (classifier 側) が存在しないから
なぜ3: 分類試行の語彙が wire 実装に吸い上げられたまま出てこなかったから
根因: attempt seam の語彙に正しい出口がない — 新設 (A) または同居 (B) で出口を作るのが根因への対処

### M3: なぜ core/classifier.ts は「message 語彙を core に持ち込まない」と言うのか
なぜ1: core が wire 語彙に依存すると core 純粋性が崩れるから
なぜ2: 現在の語彙は core 側の意味論を含む (分類試行の失敗) のに wire file に住むから
なぜ3: 意味論と運搬の同居が語彙の位置判断を難しくしているから
根因: コメントが語彙の正しい家 (core の意味論・wire でない) を指している — A/B はどちらもこの方向。C (llm) はコメントの意図に反する

### M4: なぜ META_CLIP_LENGTH が messages.ts にあるのか
なぜ1: clip 結果を wire で運ぶ場面があったから
なぜ2: 定数の意味 (prompt の表示幅) ではなく使用場面 (wire) で場所を決めたから
なぜ3: 使用場面中心の配置が定数の散在を生んできたから
根因: 定数は「使う側が所有する」— A/B/C いずれでも messages から出る必要があり、移設先は消費側 (prompt / feedback)

### M5: なぜ messages.ts の export が 36 に育ったのか
なぜ1: wire 関連の新語彙が追加のたびに messages.ts に足されたから
なぜ2: 「とりあえず共有する場所」として messages.ts が機能していたから
なぜ3: 共有場所の責務境界が文書化されていなかったから
根因: god module 化の初期段階 — 責務境界 (envelope + codec のみ) を文書と構造で固定するのが移設の副次的効果

### M6: なぜ PBI-46/54 で codec 化しても語彙が残ったのか
なぜ1: codec 化の対象は運搬の機構 (encode/decode) で、payload の語彙は範囲外だったから
なぜ2: 語彙の移設は消費者 8 module の import 書き換えを伴うから
なぜ3: 変更の限定的な範囲で止めたから
根因: 部分改善で語彙が取り残された — 本 PBI はその残務であり、再-export 移行で消費者書き換えを段階化すれば当日中に完結する

### M7: なぜ移設先候補が core/classifier 隣接なのか
なぜ1: 失敗語彙は分類試行 (attempt) の語彙だから
なぜ2: attempt seam (classifier.ts / background-gateway / classify-transport) が語彙の供給と消費の両方に接しているから
なぜ3: core は DOM・LLM 非依存で、語彙は意味論だけを持つから
根因: attempt seam の語彙は core 配下が正しい — 供給源 (llm) 配下 (C) は依存方向を逆にする

### M8: なぜ新設 (A) と同居 (B) の選択が問題になるのか
なぜ1: classifier.ts は分類の契約・純粋関数を持ち、すでに責務が多いから
なぜ2: 失敗語彙は fold 群 (数個の関数 + 型) で独立して pin 可能だから
なぜ3: 分離すると語彙のテストが語彙の横に置けるから
根因: A は「語彙の家 + 語彙のテスト」を揃え、B は classifier.ts を複合化する — B は根因 1 (同居) を別 file で再演する

### M9: なぜ re-export 移行で安全に動かせるのか
なぜ1: 型と関数の移設は値の意味を変えないから
なぜ2: importer 25 は typecheck で機械的に検出できるから
なぜ3: re-export を 1 commit だけ残せばテストは緑のまま段階的に張り替えられるから
根因: 移設リスクは手順で消せる — 移設先の選択 (A/B/C) が唯一の実質判断

### M10: なぜ今まで起票されなかったのか
なぜ1: 語彙の消費者 8 module は動いていて痛みが局所的だったから
なぜ2: 痛みは「語彙を触る時だけ」に現れるから
なぜ3: 語彙を触る機会が PBI-226/229 系の分類修正までなかったから
根因: 語彙を次に触るタイミング (来る) の前に動かすのが最も安い — 今が着手窓

## 開発運用の立場

### D1: なぜ語彙変更の PR が messages.ts に触るのか
なぜ1: 語彙の定義と re-export が messages.ts にあるから
なぜ2: messages.ts は wire 契約の見張り対象 (レビュー慎重化) だから
なぜ3: 狭域変更が広域レビューの枠に入るから
根因: 語彙を messages から出せば PR のレビュー観点が正しい粒度になる

### D2: なぜ wire テストが語彙変更で red になりうるのか
なぜ1: 語彙の fold 群のテストが messages 系テストと同居しているから
なぜ2: codec テストが語彙の具体値を fixture に使っているから
なぜ3: 語彙と運搬のテスト境界が曖昧だから
根因: テストの境界が file の同居に引きずられている — 移設で境界が明示的になる

### D3: なぜ Firefox build の分岐が増えないのか (移設しても)
なぜ1: 語彙は import.meta.env.FIREFOX 分岐を含まないから
なぜ2: 分岐は selectableProviders / normalizeAiSettings 側にあるから
なぜ3: 語彙は意味論のみだから
根因: 移設は build 分岐に触れない — A/B/C のリスク差はここに現れない

### D4: なぜ eval pin が語彙変更で壊れないのか
なぜ1: eval は分類結果と trace を pin し、失敗語彙の文言を pin しないから
なぜ2: 語彙は分類の入出力でなく「試行の成否と理由」だから
なぜ3: pin が分類挙動の保守に集中しているから
根因: 移設は eval pin に触れない — A/B/C の差は eval リスクに現れない (移設の安全網は codec pin + 新設 module の pin)

### D5: なぜ循環依存リスクがあるのか (C を選んだ場合)
なぜ1: 失敗語彙を src/llm/ に置くと、core 側の消費者 (分類パイプラインの判断) が llm を import するから
なぜ2: core は DOM・LLM 非依存が規約だから
なぜ3: 規約を守るなら core 側消費者は語彙の写しを持ち始めるから
根因: C は依存方向の逆転で重複を生む — A/B は core 内で完結し規約と整合する

### D6: なぜ codec 契約のレビュー負担が大きいのか
なぜ1: messages.ts の diff が wire 影響の有無を自動で語らないから
なぜ2: 語彙変更と wire 変更が同じ file の diff に混ざるから
なぜ3: レビュアーが手動で分類しているから
根因: 責務分離がレビューの自動化 (diff 観点の推論) を妨げている — A で語彙 file が分かれれば messages.ts の diff は wire だけを語る

### D7: なぜ「使用場面で場所を決める」パターンが再発するのか
なぜ1: 共有場所の規約 (何を置いてよいか) が文書化されていないから
なぜ2: messages.ts が先例として使われ続けるから
なぜ3: 先例が破綻の兆候 (export 36) を示しても代替の家がないから
根因: 代替の家 (A) を作り CONTEXT.md に語彙の所在を書くことで再発を止める — B では「家が 1 つ増えない」だけで先例の吸引力は残る

### D8: なぜ移設のタイミングが今よいのか
なぜ1: 語彙を触る分類修正波 (226/229 系) が収束したから
なぜ2: 語彙 module の追加 (250) と層検査を後続に置けるから
なぜ3: 変更対象が先週のレビューで 2 観点 (System Architect, API & Contract) から確認済みだから
根因: 着手窓が開いている — 次の語彙修正が来る前に出すのが最安

### D9: なぜ移設は 250 (import 方向検査) と相性がよいのか
なぜ1: 失敗語彙の正しい依存方向 (llm → 語彙 ← 消費者) が明示的になるから
なぜ2: 語彙 module が 1 個増えるだけで検査の対象パターンに載るから
なぜ3: 禁止辺 (語彙 → classify-rules 等) が機械的に守られるから
根因: A の新設は層検査の最初の受益者になる — C は検査に違反する方向 (core → llm) を誘発する

### D10: なぜ wire 形式を変えずに語彙だけ動かせるのか
なぜ1: 語彙 (型と fold 関数) は wire キー名と直交しているから
なぜ2: wire キーは REQUEST_WIRE_KEYS 表 (PBI-190) で表駆動管理だから
なぜ3: 語彙の移設は import 経路の変更だけで、表と encode/decode は無変更だから
根因: 技術的な分離コストはほぼゼロ — 判断は純粋に「家をどこに置くか」

## 支配的構造根因 (30 本の集約)

1. **運搬経路と意味の同居** — 失敗語彙は wire payload として生まれ、運搬層に住んだまま成長した。意味 (語彙) の家は運搬層の外にあるべき (U2, M1, M2, D1, D10)。
2. **attempt seam の語彙に正しい出口がない** — 分類試行の語彙なのに classifier 側から出口がなく、8 module が wire 経由で拾いに来ている (M2, M3, M7, D5, D9)。
3. **「使用場面で場所を決める」先例の吸引力** — META_CLIP_LENGTH のような非 wire 定数まで集積し、export 36 の god module 化が進んだ。代替の家がないことが再発条件 (U6, M4, M5, D7)。

## 候補評価と決定の導出

| 根因 | A) classifier-failures 新設 | B) classifier.ts 同居 | C) llm 側 |
|---|---|---|---|
| 1 運搬と意味の同居 | 解消 (専用の家) | 半分解消 (messages から出るが classifier が複合化) | 解消しない (wire 隣接の同居が続く) |
| 2 attempt 語彙の出口 | 解消 (語彙 + pin が seam の横) | 解消 (出口はできる) | **悪化** (core 消費者 → llm 依存、core 純粋性規約に触れる) |
| 3 先例の吸引力 | 解消 (CONTEXT.md に家を記録) | 半分解消 | 解消しない (llm に新たな共有場所が増える) |

- 導出: **A (core/classifier-failures.ts 新設)** が 3 根因を最も直接に解く。B は根因 1 を半分だけ解き classifier.ts を複合化する。C は根因 2 を悪化させ (core → llm の依存逆転)、core 純粋性の規約に触れる。
- 移設手順は re-export 1 commit → importer 張り替え → re-export 撤去 (M9/D10: 技術リスクはほぼゼロ)。
- 受容するリスク: 新 module が 1 個増える (ファイル数の増加)。CONTEXT.md に所在を記録し、250 の層検査に載せることで手当てする。
